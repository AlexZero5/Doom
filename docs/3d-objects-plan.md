# План: настоящий 3D-слой в FunDoom (объекты-«кубы» с произвольной детализацией)

> Автор: Qwen Code, 2026-10-06. Статус: **РЕАЛИЗОВАНО (фазы 1–5), 9/9 харнесс-проверок зелёные, 2.1 мс/кадр 280×70 с демо-сценой.**
> Ключевые грабли первого захода (устранены): (1) знак отсечения задних граней был перепутан — рисовались только «крышки», вертикальные грани отбрасывались; (2) instance.Z не прибавлялся к вершинам; (3) вертикальные квады требуют отдельного пути (2D-клип вырождается); (4) демо-объекты стояли далеко/за стенами — переставлены к старту.
> Базовая точка: коммит `2b1730a` (рабочий билд, качество на лету, полы/потолки, скайбокс, наклон).
> **Обновление 2026-10-19:** растеризатор переписан (буфер глубины, подготовка граней раз в кадр, треугольники), исправлены нормали горизонтальных граней, пандус и коллизии; камера стала честной (без «рыбьего глаза», квадратные пиксели). Подробности — в [code-review.md](code-review.md). Описание «slab-списка» и проекции ниже устарело.

## 1. Что хочет пользователь (ТЗ своими словами)

1. Карта перестаёт быть чисто псевдо-3D (плоский 2D-массив): добавляется **третья ось Z**, объекты размещаются в мире как **кубы** (x, y, z).
2. Объект — «куб» с **неограниченным внутренним разрешением**: между x=1 и x=5 может уместиться хоть 200 единиц объекта (подразумевается: подразбиение сеткой/полигонами — рельеф, наклоны, круги).
3. По рендеру: **сколько лучей попадает на объект — столько и рисуется** (растеризация по колонкам, разрешение экрана не влияет на геометрию).
4. Это открывает: **рельеф** (неровная земля), **наклонные поверхности** (пандусы), **круглые формы** (цилиндры/диски — «было бы прикольно»).
5. Объектам можно **задавать вращение**.
6. Текстуру можно натягивать **на каждый отдельный полигон**.
7. Пользователь принимает, что **производительность рендера упадёт** («размер рендера меньше станет»).
8. Двери — по-прежнему отложены (последний приоритет, не в этом плане).

## 2. Анализ текущего кода (что имеем, факты)

### 2.1. Рендер-конвейер (SceneRenderer.Render, Doom/Rendering/SceneRenderer.cs)

Порядок отрисовки кадра:
1. **Пол/потолок/небо** на всю колонку (`FloorAtPixel` / `CeilingOrSky` / `SkyAtPixel`) — строятся из покадровых кэшей по строкам (`_floorRowDistance`, `_ceilingRowDistance`, `_skyTexV`), семплируются **без поправки на «рыбий глаз»** (осознанное решение — см. память world-render; иначе стык пола со стенами ломается).
2. **Стены** — `Raycaster.CastAll` (DDA по 2D-сетке, до 4 сегментов на луч), рисуются от дальних к ближним (`PaintWallSlab`), текстурная V привязана к мировой высоте (`WorldZAt`), затенение через `WallShader.ColumnShader.ShadeSpan`.
3. **Спрайты** (бонусы, снаряды, взрывы) — проецируются в `SpriteQuad` (`SpriteProjector.AddQuad`), сортируются по глубине, рисуются с проверкой перекрытия стенами этой колонки (`HiddenByWall` по интервалам slab-ов: до 4 стеновых + локальные stackalloc-массивы).

Ключевая математика проекции (используется ВЕЗДЕ, её нельзя менять):
- экранная колонка `x` → угол луча `rayAngle = angle − halfFov + fov·(x+0.5)/columns`;
- экранная строка «пикселя» `p` → `screenY = horizon + PixelRows·(CameraZ − z) / perpDist`, где `horizon = HorizonPixels(pitch)` (Y-shear), `CameraZ = 0.5`, `perpDist` — перпендикулярная дистанция;
- яркость = `LightRange/(dist+LightOffset)`, гамма 1/1.6, тень боковых граней 0.78.

**Важное свойство:** при Y-shear наклоне камеры луч колонки в горизонтальной плоскости НЕ меняется (наклон влияет только на вертикальную проекцию). Это значит, что для любой 3D-геометрии можно растеризацию вести по колонкам тем же способом, что и стены: 2D-пересечение луча колонки с проекцией объекта, а вертикаль решать на плоскости полигона.

### 2.2. Мир (Doom/World/)

- `Level` — три слоя `int[,]`: стены (коды 1..5 полные, 11..15/21..25 низкие — движок поддерживает, но на карте не используются), полы, потолки. `IsWalkable` = клетка 0.
- `DefaultMap.Create()` — карта строится кодом: 4 здания (record `Building`), тропы, колонны. Бонусы `PickupLayout` лежат в интерьерах — при изменении карты сверять координаты.
- Игрок ходит по 2D-сетке (`Player.Move` скользит по стенам), снаряды — `ProjectileSystem` (пол/потолок/стены, высота Z у снарядов уже есть).

### 2.3. Ограничения, которые нельзя ломать (память working-build-baseline)

- Двойной режим терминала (conhost/ConPTY), зум от Ctrl+0, фокус перед каждым нажатием — не трогать.
- Пол/потолок без поправки на «рыбий глаз» — не возвращать cosRel.
- Рендер параллельный (`Parallel.For` по колонкам) — любое новое состояние должно быть либо покадровым read-only, либо локальным для колонки (гонка `_slabCount` уже ловилась).
- ~60 FPS, redraw по изменениям; кадр 280×70 сейчас ≈ 1.2 мс в Debug — есть большой запас.

## 3. Архитектурное решение

**Гибрид: 2D-рейкастер остаётся фоном, 3D-объекты — отдельный слой растеризации по колонкам.**

Полноценный 3D-DDA по вокселям — это переписывание всего рендера с высоким риском сломать работающее (и память прямо требует инкрементальности). Вместо этого:

- **Фон** (небо, пол, потолок, стены сетки) рисуется как сейчас — быстро и проверенно.
- **3D-объекты** — новый слой: мир хранит список **экземпляров** (`ObjectInstance`: позиция x,y,z + вращение по yaw + масштаб + меш + текстура), каждый меш — список **ориентированных 3D-квадов** (полигонов) с UV. Квады растеризуются по колонкам **точно той же проекцией**, что и стены/спрайты, поэтому всё идеально стыкуется.
- Воксельная детализация («200 единиц между 1 и 5») достигается **подразбиением**: генераторы мешей умеют нарезать квад сеткой любой плотности (heightfield, цилиндр из N граней, пандус из N ступеней-квадов). Каждый под-квад — самостоятельный полигон со своей текстурой, если хочется.
- «Сколько лучей попало — столько и нарисовано» выполняется автоматически: растеризация по колонкам.

### 3.1. Математика растеризации квада по колонке (точная, дешёвая)

Для колонки `x` известен луч в горизонтальной плоскости: направление `(dirX, dirY)`, угол `rayAngle`.
Квад задан 4 вершинами в мировом пространстве (уже трансформированными: позиция + yaw + масштаб).

1. **2D-клип**: пересекаем 2D-луч (как отрезок из игрока в бесконечность) с проекцией квада на XY (выпуклый четырёхугольник) — получаем вход `t0` и выход `t1` (дистанции вдоль луча). Если нет пересечения — квад не виден в этой колонке.
2. В точках t0/t1 считаем **Z и UV** — они линейны вдоль прямой внутри плоскости квада (квад планарен, UV аффинны).
3. **Перпендикулярная дистанция** `perp(t) = t·cos(rayAngle − playerAngle)`.
4. Для каждого экранного «пикселя» `p` в вертикальном диапазоне квада: уравнение `screenY(p) = horizon + PixelRows·(0.5 − z(t)) / perp(t)` при линейном `z(t)` — **линейное уравнение относительно t**, решается в одну строку. Далее UV по t, сэмпл текстуры, затенение по дистанции.
5. **Глубинные проверки на пиксель**: пиксель закрыт стеной этой колонки (slab ближе) → пропустить; сам квад записывает свой интервал глубины для перекрытия спрайтов.

Квады рисуются в колонке от дальних к ближним (painter's algorithm) — перекрытия объектов решаются сами. Два пересекающихся в пространстве объекта могут глитчнуть на линии пересечения — приемлемо (и обходится генерацией мешей без самопересечений).

### 3.2. Глубина и спрайты

Сейчас спрайты проверяют `HiddenByWall` по стеновым slab-интервалам колонки. Расширение: после отрисовки объектов колонки их интервалы **дописываются в тот же список slab-ов** (лимиты: стены 4 + объекты до 12 → буфер 16, stackalloc). Спрайты за объектами корректно скроются, снаряды перед объектами — нарисуются.

### 3.3. Столкновения (минимум, честный)

- Игрок: объект имеет **2D-футпринт** (круг радиуса или AABB) — `Player.Move` скользит по нему так же, как по стенам (проверка до и после шага по осям).
- Снаряды: проверка попадания в AABB объекта на текущем шаге полёта (`ProjectileSystem.AdvanceThroughLevel` + объектный тест); взрыв как о стену, точка попадания на грани.
- Хождение ПО объектам (по рельефу) — **не в этой фазе** (игрок остаётся на z=0.5); рельеф пока декоративно-препятственный. Это честно зафиксировано в плане (см. §8 «Что сознательно откладываем»).

## 4. Новые типы и файлы

```
Doom/World/
  Mesh3D.cs           — меш: массив OrientedQuad3D (вершины, UV-углы, текстура per-quad, яркость)
  Quad3D.cs           — ориентированный полигон: 4 вершины (X,Y,Z), UV, флаги (двусторонний)
  MeshFactory.cs      — генераторы: Box, Cylinder(граней, радиус, высота), Disc, Ramp,
                        Heightfield(функция высоты, подразбиений), Stairs
  ObjectInstance.cs   — позиция (X,Y,Z), поворот yaw, масштаб, меш, текстура-переопределение,
                        футпринт для коллизий, флаг «твердый»
  WorldObjects.cs     — список экземпляров уровня + покадровая выборка видимых
Doom/Rendering/
  ObjectRasterizer.cs — растеризация квадов по колонке (математика §3.1, затенение, сэмплы)
```

Изменения в существующих:
- `Level` (+`Objects` ссылка или отдельный параметр) — минимально; **слои сетки не трогаем**.
- `SceneRenderer.RenderColumn` — между стенами и спрайтами вызов растеризатора объектов; slab-буфер расширяется до 16.
- `SpriteProjector` — без изменений (перекрытие обеспечит общий slab-список).
- `Player.Move` / `ProjectileSystem` — коллизии с футпринтами объектов.
- `DefaultMap` (+`DefaultProps`) — демо-объекты: круглая башня (цилиндр), пандус, рельеф-холм heightfield, наклонная крыша на здании? (решим при реализации), диск-«тарелка».
- `GameConfig` — лимиты: `MaxObjectQuadsPerFrame`, `MaxObjectDistance` (отсечение дальних), `MaxDepthSpansPerColumn = 16`.
- `GameSettings` (опционально, потом) — «Детализация объектов» (низкая/средняя/высокая) → множитель подразбиения.

## 5. Фазы внедрения (каждая фаза = рабочая, собираемая, проверяемая)

**Фаза 1 — ядро геометрии (без рендера).**
`Quad3D`, `Mesh3D`, `MeshFactory` (Box, Cylinder, Disc, Ramp, Heightfield), `ObjectInstance`, `WorldObjects`.
Проверка: юнит-харнесс — генераторы дают ожидаемое число квадов, вершины в границах, поворот считается правильно.

**Фаза 2 — растеризация.**
`ObjectRasterizer`: клип квада колонкой, линейное решение по `t`, UV/сэмпл/затенение; интеграция в `SceneRenderer` (слой между стенами и спрайтами, slab-список 16).
Проверка: харнесс рендерит сцену с одним боксом на известной позиции — колонки/строки попадания совпадают с ручным расчётом; объект за стеной скрыт; объект перед стеной рисуется поверх; спрайт за объектом скрыт.

**Фаза 3 — вращение и текстуры per-polygon.**
Yaw-трансформация вершин экземпляра (покадрово, дёшево — 4 вершины на квад), текстура на квад (в т.ч. разные на гранях бокса).
Проверка: повёрнутый на 45° бокс рендерится без разрывов; цилиндр из 12 граней выглядит круглым.

**Фаза 4 — мир и коллизии.**
`DefaultProps`: демо-расстановка (башня-цилиндр с текстурой стен 3, пандус-рампа к холму, heightfield-холм с травой 6, диск). Коллизии игрока (футпринт) и снарядов (AABB).
Проверка: в башню нельзя войти сквозь стену, снаряд взрывается о неё; на рампу нельзя «зайти» (пока препятствие), пули дают искру на грани объекта.

**Фаза 5 — производительность и полировка.**
Отсечение по дистанции (`MaxObjectDistance`), по FOV (сферический/аэреббатический тест меша), сортировка мешей по дистанции; при желании — настройка детализации. Замер перфа харнессом (цель: кадр 280×70 с демо-сценой ≤ 4 мс Debug).
Проверка: FPS на «Ультра» остаётся играбельным; artifacts отсутствуют.

**Фаза 6 — документация.**
README (раздел «3D-объекты»), память `world-render.md` — дополнить архитектурой.

## 6. Риски и как их гасим

| Риск | Митигация |
|---|---|
| Перф: много квадов (heightfield 32×32 = 1024 квада) | Отсечение по дистанции/FOV; подразбиение умеренное (8–16 на клетку); сортировка по дистанции один раз за кадр; растеризация только видимых колонок |
| Швы между соседними квадами heightfield (зубцы) | Рисование с полу-пиксельным перекрытием (общая вершина → общая граница), как у стен сейчас (`PixelCoverage`) |
| Глитчи пересекающихся объектов | Запрет пересечений в генераторах; painter's algorithm допускает лёгкие огрехи |
| Гонки Parallel.For | Все данные покадровые read-only после подготовки; на колонку — только stackalloc-спаны (усвоенный урок `_slabCount`) |
| Стык объектов со стенами/полом | Та же проекция и то же затенение, что у стен; высоты объектов задаются в тех же единицах (1.0 = высота стены) |
| Сложность отладки «на глаз» | Фаза 2 сначала в харнессе с численными проверками (колонки/строки/глубина), потом в игре |

## 7. Что пользователь получит на выходе (демо-сцена)

- Круглая башня (цилиндр, текстура крио-тех 3) во дворе — «круг» из ТЗ.
- Наклонный пандус (рампа) с текстурой песчаника 4 — «наклон».
- Холм-рельеф (heightfield, трава 6) с плавными склонами — «рельеф» и «200 единиц между 1 и 5» (подразбиение 16×16 на клетку).
- Вращающийся «куб-артефакт» (бокс с текстурой кристалла 5, медленное вращение) — «вращение» и «текстурка на каждый полигон» (грани разными кадрами одной текстуры).

## 8. Что сознательно откладываем (честно)

- **Хождение по рельефу** (игрок на высоте поверхности, подъём по рампам) — отдельная фаза после базового слоя: нужны высота игрока, гравитация/ступени и переработка `IsWalkable` в 3D.
- **Двери** — по-прежнему последний приоритет (решение пользователя).
- **Полноценный воксельный реймарч** (3D-DDA по плотной сетке) — если гибрида окажется мало; гибрид покрывает рельеф/наклоны/круги дешевле.
- **Ролл камеры** (наклон головы вбок) — не запрошен.

## 9. Критерий готовности

1. Все фазы собраны, харнесс-проверки зелёные (геометрия, проекция, окклюзия, коллизии, перф).
2. В игре: башня круглая, пандус наклонный, холм рельефный, куб вращается; стены/полы/потолки/спрайты ведут себя как раньше (ничего не сломано).
3. Кадр 280×70 с демо-сценой ≤ 4 мс (Debug); на «Ультра» играбельно.
4. Коммит — только по явной команде пользователя.
